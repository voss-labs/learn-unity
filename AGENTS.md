# learn-unity: Project Instructions

learn-unity is how VOSS Labs students learn Unity: they walk a world, open its code, change it, and ship their own world by pull request. Readers are second-year engineering students. Optimise every change for someone who has never opened Unity, and who may never meet you.

CLAUDE.md is symlinked to this file, so the same content applies to all coding agents.

## Layout

- The repo root is the Unity project. Open it directly in Unity Hub
- `Assets/Core/`: shared by every world: `Walker.cs`, `TouchControls.cs`, `Hud.cs`, `WideView.cs`, `PhoneSettings.cs`, `Spinner.cs`, `Player.prefab`. A change here affects every world
- `Assets/Worlds/<Name>/`: one world. It must hold `<Name>.unity` and `README.md`. Worlds never reference each other
- `Assets/Editor/`: `NewWorld.cs` (the New world window) and `WebBuild.cs` (web builds)
- `Assets/WebGLTemplates/Walk/`: the page every world loads in
- `docs/`: setup, the numbered lessons, and how to add a world
- `site/`: what Vercel serves. The landing page plus `site/<world>/`, built by Unity and committed. Each world has a computer data file (DXT) and a phone one (`*.mobile.data.unityweb`, ASTC with smaller textures)
- `scripts/check.mjs`: repo checks, with tests in `test/`. Node standard library only

## Commands

- `node scripts/check.mjs`: check the repo. Run before every commit
- `node --test`: test the checks
- `./scripts/build.sh [World...]`: build web builds into `site/`. Needs the Unity CLI and Web Build Support
- `npx http-server site -c-1`: serve the site locally

## Rules

- Lessons explain the code, so code stays free of comments. If you change code that a lesson quotes, update the lesson in the same commit. `check.mjs` catches file paths that no longer exist, but not quoted code that has drifted
- If an exercise in a lesson stops working, it is a bug. Lessons are the product
- With a live Editor open, change scenes through the Editor (`unity command`), never by hand-editing `.unity` or `.prefab` files
- Move and rename assets inside Unity, or move their `.meta` files with them. Keep GUIDs unique. `check.mjs` catches both mistakes
- Contributors do not commit `site/`. Maintainers rebuild only the worlds that changed
- Every world must run on iPhone and Android. Never gate a world by device. Watch the unpacked size, not just the download: the build log's `Textures` line is what a phone must hold in memory
- Match the VOSS brand as it is on GitHub, in `voss-labs/vosslabs.org`: the tokens in `src/styles/global.css` and the kit in `public/brand/`, Geist and Geist Mono, the VOSS wordmark with its orange square, light by default with a dark theme. Do not invent a palette
- Web builds use Brotli with Decompression Fallback, so that no server headers are needed. Do not switch to `.br` files: Vercel can double-compress them. Lesson 6 explains why
- Assets must be CC0 or similarly free to share, and credited in the world's README
- Campus's `campus.glb` and `textures/` are generated by vmaps (`npm run export:unity`). Do not edit the campus model here. Change it in vmaps and export again
- Keep folders flat, files under 400 lines, and no emojis anywhere. Commit messages are conventional commits

## Verifying a change

A green `check.mjs` is the floor, not the verdict. Press Play in every world you touched. For anything that affects web builds, build it and walk it in a real browser with the console open, on a computer and on a phone or phone simulator.
